# Pocket Billiards — технический дизайн-документ (TDD)

Версия 0.1 · 3D-бильярд (8-Ball / 9-Ball) для Android · open-source (MIT)

---

## 0. Выбор движка: Unity 6 (LTS) + URP + C#

| Критерий | Unity 6 + URP | Godot 4.x |
|---|---|---|
| Android-пайплайн (AAB, 64-bit, 16 KB pages, target API 36) | зрелый, из коробки | работает, но больше ручной работы |
| Производительность C# на ARM64 | IL2CPP → нативный код | GDScript медленнее; C# на Android всё ещё не первоклассный |
| Мобильная графика (PBR, reflection probes, shader LOD, адаптивное качество) | URP + Adaptive Performance | Mobile renderer проще, меньше инструментов профилирования |
| Ads / IAP / Play Games / Remote Config | официальные пакеты | сторонние плагины |
| Онлайн позже | Netcode for GameObjects, Unity Relay/Lobby, или свой сервер | ENet/WebRTC вручную |
| Профилирование на устройстве | Profiler, Memory Profiler, Frame Debugger, Android Logcat | слабее |

**Решение: Unity 6 LTS + URP + C#.** Главный аргумент — не «PhysX лучше», а то, что физику мы пишем **сами** в отдельной сборке без зависимостей от движка. Unity нужен как рендер + платформа + экосистема Android. Если когда-нибудь захочется Godot, ядро физики (`Billiards.Physics`) переносится без изменений — это обычный C#.

Лицензия движка: open-source-код игры (MIT) спокойно живёт на Unity; ассеты из Asset Store в репозиторий класть нельзя — только свои/CC0-модели и текстуры.

### 1.3 Сцены

- `Boot` — инициализация сервисов (сохранения, настройки, локализация, Remote Config), переход в меню. Пустая и мгновенная.
- `Menu` — главное меню, выбор режима, магазин/кастомизация, настройки.
- `Match` — стол, игра. Одна сцена на все режимы; режим задаётся `MatchSettings` (ScriptableObject/DTO), переданным из меню.

Загрузка через Addressables: столы и кии — отдельные бандлы, чтобы базовый AAB оставался маленьким.

Каждое состояние — класс с `Enter/Tick/Exit`. Переход хода и онлайн позже работают через одну точку: «к столу пришёл `CueStrike`». Источником может быть тач-ввод, ИИ, реплей или сеть.

### 1.5 Менеджеры / сервисы

Без синглтонов-«богов». Небольшой `ServiceLocator` (или VContainer, если команда растёт), регистрирует в `Boot`:

- `ISaveService` — JSON в `Application.persistentDataPath`, версия схемы, позже облачное сохранение.
- `ISettingsService` — графика, чувствительность, aim-assist, звук, вибрация.
- `IAudioService` — пул `AudioSource`, громкость от `PhysicsEvent.Speed`.
- `IHapticsService` — короткая вибрация на удар/лузу.
- `IProgressionService` — монеты, XP, разблокировки столов/киев.
- `IAdsService` / `IIapService` — интерфейсы с пустой реализацией в open-source-сборке (в форках подключают реальные SDK).

## 2. Физика (самое важное)

Реализовано в `Assets/_Project/Scripts/Physics`, покрыто тестами.

### 2.1 Почему не PhysX

PhysX — игровой движок общего назначения: нет режимов «скольжение/качение», вращение шара не влияет на траекторию правильно, трение ball-ball (throw) и борт с «english» не моделируются, результат зависит от FPS и платформы. Для бильярда это всё критично. Поэтому шары в Unity — только визуал, вся динамика своя.

### 2.2 Модель

Координаты как в Unity: X — длинная ось стола, Y — вверх, Z — короткая ось. Сукно — плоскость Y=0, центр лежащего шара на Y=R. Всё в double.

**Состояния шара** (`BallMotion`): `Stationary`, `Spinning` (крутится на месте вокруг вертикали), `Sliding`, `Rolling`, `Airborne`, `Pocketed`, `OffTable`.

**Уравнения** (точка контакта с сукном r = (0, −R, 0), скорость проскальзывания u = v + ω × r):

| Режим | Линейная | Угловая |
|---|---|---|
| Sliding | dv/dt = −μs·g·û | dω/dt = (r × F)/I = (5μs·g / 2R)·(ûz, 0, −ûx) |
| Rolling | dv/dt = −μr·g·v̂ | ωx = vz/R, ωz = −vx/R (жёсткая связь) |
| Все на сукне | — | dωy/dt = −sign(ωy)·α_spin |
| Airborne | dv/dt = −g | ω = const |

Ключевое свойство: в скольжении |u| убывает линейно со скоростью (7/2)·μs·g, направление û постоянно. Поэтому момент перехода «скольжение → качение» внутри шага вычисляется аналитически (`IntegrateSliding`), а не «примерно». Из этого автоматически следуют: правило 5/7 (stun-шар катится на 5/7 начальной скорости), оттяжка, накат, кривая траектории при масse.

**Удар кием** (`CueStrikeModel`): кий — свободная масса M, импульс J вдоль оси кия d в точке контакта r на поверхности шара:

```
J = (1 + e_tip) · V0 / (1/M + 1/m + |r × d|² / I)
v = J·d / m          ω = (r × J·d) / I
```

- Смещение по вертикали (b) → накат/оттяжка, по горизонтали (a) → боковое вращение.
- Возвышение кия наклоняет d вниз → шар вдавливается в сланец → отскок → **прыжок**. Возвышение + боковое смещение → ось вращения наклонена → трение скольжения закручивает траекторию → **массе**.
- **Squirt** (отклонение битка от боковика) по формуле Alciatore через «end mass» древка; разные кии = разная end mass → реальная разница между «low-deflection» шафтом и обычным.
- Ограничение смещения кругом 0.5R; за пределом — кикс (ослабленный импульс).

**Столкновения** — единая функция «импульс в точке контакта + кулоново трение, ограниченное импульсом, останавливающим проскальзывание»:

| Контакт | Нормаль | e | Трение | Что даёт |
|---|---|---|---|---|
| Шар–шар | линия центров | 0.95 | μ(v)=0.00995+0.108·e^(−1.088v) (Alciatore) | cut-induced и spin-induced throw, передача вращения |
| Шар–борт | от носа борта (высота 0.0363 м, выше экватора) | 0.85, падает со скоростью | 0.2 | «running/reverse english», потеря энергии, небольшое прижатие к столу |
| Шар–сланец | вверх | 0.5 | 0.2 | приземление после прыжка |

**Шар–шар без туннелирования:** после шага для каждой перекрывающейся пары решается квадратное уравнение |(pA−vA·t) − (pB−vB·t)| = 2R, шары откатываются на t назад, импульс применяется в точной геометрии касания, затем доводятся вперёд. Это держит углы резки точными даже на разбое.

**Шаг интегрирования** фиксированный: 1/1200 с. При 12 м/с шар проходит < 0.35R за шаг. Фиксированный (а не адаптивный) шаг даёт результат, не зависящий от FPS устройства → детерминизм: одинаковое состояние + одинаковый `CueStrike` = одинаковый исход. На этом строятся реплеи, ИИ, онлайн.

**Борта и лузы** (`TableGeometry`): носы бортов — отрезки; концы отрезков работают как скруглённые «губки» луз. Лузы — окружности захвата. Всё задаётся числами: 7/8/9-футовые столы, «тугие» лузы для сложного режима — без изменения кода. В редакторе геометрия рисуется гизмо.

### 2.3 Производительность

- Пары покоящихся шаров не проверяются; шары далеко от бортов не проверяют борта (broad phase); покоящиеся шары не проверяют лузы.
- В `Step()` нет аллокаций; состояние стола — массив структур → клонирование одним `Array.Copy`.
- Замер (desktop Mono JIT, без IL2CPP): разбой из 16 шаров досчитывается до остановки за ~15 мс; 200 случайных ударов ИИ — ~3 с. На телефоне под IL2CPP ожидаем тот же порядок; ИИ дополнительно использует грубый шаг (1/600) для отбора и точный — только для финалистов.

### 2.4 Тесты (EditMode, `PhysicsTests.cs`)

Каждый тест проверяет учебный результат: правило 5/7; дистанция качения v²/(2μr·g); прямой stun-удар передаёт ~97.5% скорости; правило 90° при резке (с реальными потерями ~86°) и cut-induced throw 1–5°; оттяжка возвращает биток; накат проводит его вперёд; отскок от борта с e≈0.85; боковое вращение уводит отскок; прыжок при возвышении кия; детерминизм разбоя; корректная расстановка; aim-предсказание. CI (GitHub Actions + game-ci) гоняет их на каждом PR.

### 2.5 Тюнинг «ощущения стола»

`PhysicsConfig` (ScriptableObject) открывает дизайнеру: μ скольжения/качения, затухание вращения, упругость шаров и бортов, множитель throw, массу кия, end mass (squirt), максимальную силу. Разные сукна — разные ассеты. Значения по умолчанию взяты из опубликованных измерений (Marlow; Alciatore; Mathavan et al.).

## 3. Управление: прицел, сила, вращение

Принцип: **виджеты только вызывают методы `ShotController`**; ИИ вызывает те же методы. ИИ физически не может сделать то, чего не может игрок.

### 3.1 Прицел (`AimTouchArea`)
- Невидимая полноэкранная UI-панель под HUD (EventSystem → одинаково работает с тачем, мышью, старым и новым Input System).
- Тянешь палец в любом месте → прицел поворачивается на угол, который палец «заметает» вокруг битка **на плоскости сукна** (проекция луча). Одинаково интуитивно в 3D и top-down.
- Тап без перетаскивания → прицел прямо на точку.
- Отдельная узкая полоска сбоку (`fineMode`) → вертикальный свайп крутит прицел в 15–20 раз медленнее для точной резки.
- Два пальца → pinch-zoom камеры.

### 3.2 Сила (`PowerSlider`)
- Вертикальная полоса у правого края (под большой палец). Нажал → тянешь вниз = оттягиваешь кий → отпустил = удар. Вернул вверх → отмена.
- Нелинейная кривая (`AnimationCurve`): нижние 50% хода дают ~25% силы — мягкие удары контролируются точно.
- Кий визуально оттягивается пропорционально силе (`CueView`), цвет полосы — градиент.

### 3.3 Вращение / English (`SpinWidget`)
- Круг-«биток глазами игрока», точка перетаскивается. Круг отображается на допустимую зону 0.5R. Двойной тап — в центр.
- Отдельный ползунок возвышения кия (0–75°) для прыжка и массе.
- Aim-линия не пытается «угадать» влияние вращения (как в реальности — игрок учитывает сам); в Practice можно включить полный физический предпросмотр (клон мира + `SimulateToRest`, траектории всех шаров).

### 3.4 Aim-линия (`AimPredictor` + `AimLineRenderer`)
- Геометрия без трения: свип шара (ray vs круг 2R), отражения от бортов (ray vs капсула вокруг носа борта, с учётом высоты контакта), до N отскоков.
- Показывает: путь битка, «призрачный шар», направление прицельного, касательную битка (stun, правило 90°).
- Уровень помощи — данные: число отскоков, длина линий; в «Pro» линии короткие или выключены.

### 3.5 Камера (`CameraRig`)
- Aim: позади битка вдоль прицела, наклон 18°, zoom 0.5–2.2 м.
- Во время качения — плавный отъезд на обзор стола.
- Кнопка 3D / top-down. Всё через SmoothDamp, без резких движений.

## 4. ИИ

### 4.1 Как «думает» ИИ

```
1. Кандидаты (геометрия, ~мгновенно)
   для каждого легального прицельного шара × каждой лузы:
     точка прицела в лузе (с учётом угла захода, «губок»)
     призрачный шар = центр прицельного − 2R·направление_к_лузе
     проверить: путь битка до призрачного шара свободен,
                путь прицельного до лузы свободен,
                угол резки < 80°
     оценка сложности: угол резки, расстояния, угол входа в лузу
   + банки (1 борт) и комбинации (2 шара) — для Hard+
   + «safety» кандидаты, если нет нормальных ударов

2. Отбор: топ-K кандидатов по сложности

3. Симуляция (полная физика, фоновый поток)
   для каждого кандидата × вариации силы (3–5) × вращения (stop/follow/draw, ±side):
     clone world → Strike → SimulateToRest
     ShotRecord → IRules.Evaluate → результат
     оценка позиции: сколько «лёгких» следующих ударов есть у битка

4. Выбор: max( P(забил) · (ценность позиции) − штраф за фол/проигрыш )
   P(забил) оценивается Монте-Карло: 5–10 повторов с шумом исполнения

5. Исполнение с шумом уровня сложности → ShotController.Execute(strike)
```

### 4.2 Уровни сложности (`AiProfile`, ScriptableObject)

| Параметр | Easy | Medium | Hard | (Pro, позже) |
|---|---|---|---|---|
| Шум прицела σ | 1.5° | 0.6° | 0.2° | 0.05° |
| Шум силы σ | 15% | 8% | 4% | 2% |
| Использует вращение | нет | stop/follow/draw | + side | + массе/прыжок |
| Игра на позицию | нет | 1 шар вперёд | 1 шар + оценка кластеров | 2 шара |
| Банки/комбинации | нет | банки | банки + комбо | всё |
| Отыгрыш (safety) | нет | редко | да | да |
| Бюджет симуляций | 30 | 150 | 400 | 1000 |

Шум добавляется к исполнению, а не к «мышлению» — ИИ промахивается как человек (чуть мимо), а не делает абсурдных выборов. Плюс «задержка раздумья» 0.8–2.5 с и анимация прицеливания — чтобы выглядело естественно.

### 4.3 Технически
- Расчёт в `Task.Run` на копии мира; главный поток не блокируется. Отмена через `CancellationToken` при выходе в меню.
- Детерминированный сид шума — матч против ИИ воспроизводится в реплее.

## 5. Правила

`IRules.Evaluate(ShotContext ctx, ShotRecord record) → ShotOutcome`:

- `ShotRecord` строится из `PhysicsEvent`: первый тронутый шар, все касания бортов после первого контакта, забитые шары (с лузами), вылет за стол, кикс.
- `ShotOutcome`: фол (и причина для UI), переход хода, ball-in-hand (вся площадь/«дом»), назначение групп, повторная установка шаров (9 в 9-Ball при фоле, 8 на разбое), победитель.

**8-Ball (WPA, упрощённо для v1):** легальный разбой (≥4 шаров к бортам или забитый); открытый стол после разбоя; группа назначается первым легально забитым после разбоя; фолы: биток в лузе/за столом, первым тронут не свой шар, после контакта ни один шар не коснулся борта и ничего не забито; 8 до очистки группы или с фолом → поражение. Опции: «заказ лузы» для 8-ки (по умолчанию вкл.).

**9-Ball:** первым трогается младший шар; любой легально забитый шар продолжает серию; 9 легально → победа (в т.ч. на разбое и комбинацией); фол → ball-in-hand, 9 при фоле ставится обратно; push-out после разбоя и «три фола подряд» — этап полировки.

Правила полностью покрываются табличными тестами (сценарий из событий → ожидаемый исход), без физики.

## 7. Оптимизация под Android (цель: 60 FPS на mid-range, напр. Snapdragon 6-серии / Mali-G57)

**Сборка**
- IL2CPP, ARM64 only, .NET Standard 2.1, Managed Stripping = Medium, AAB, Vulkan первым + GLES3 фолбэк.
- Target API 36 (требование Google Play для новых приложений и обновлений), min API 26–28.
- Application.targetFrameRate = 60 (опция 30 для экономии батареи; 90/120 — «High»).
- Адаптивное качество: Adaptive Performance (Samsung/Google провайдеры) + свой понижатель (разрешение рендера 0.75–1.0) при просадке.

**Рендер (URP)**
- Forward, 1 основной directional/spot свет с тенями (стол освещён лампой сверху — по сути одна тень), остальное — запечённый свет (lightmaps) и Light Probes.
- Тени: 1 каскад, 1024px, дистанция ~4 м — стол маленький, этого достаточно. Под шарами — дешёвая «blob/contact shadow» декаль для мягкости.
- Отражения на шарах: один запечённый Reflection Probe (кубмап зала) + специфика; **без** SSR и realtime-проб. Лак на бортах — тот же probe.
- Шары: одна модель (~1–1.5k трис) + атлас номеров 4×4, `MaterialPropertyBlock` / GPU Instancing → 16 шаров ≈ 1 draw call.
- Сукно: тайловая normal + detail, без параллакса. Стол: 2–3 материала, LOD не нужен (камера близко).
- Post-processing: только tonemapping (ACES/Neutral) + лёгкий bloom на High; MSAA 2x/4x вместо FXAA (на тайловых GPU MSAA дешёвый).
- SRP Batcher вкл., статический батчинг окружения, ASTC-текстуры.

**CPU**
- Физика 1200 Гц: ~20 шагов за кадр, на покое — ноль работы (стол «спит»).
- Ноль аллокаций в кадре (aim-предсказание переиспользует буферы); проверяется Profiler → GC Alloc = 0.
- ИИ — фоновый поток, в главном только применение результата.
- UI: отдельный Canvas для часто меняющихся элементов (полоса силы), чтобы не перестраивать весь HUD.

**Память/размер**
- Addressables для столов/киев/окружений; базовый модуль AAB < 200 МБ (лимит Play на сжатую загрузку), цель — 60–80 МБ.
- Аудио: Vorbis, короткие клипы — Decompress on Load, музыка — Streaming.

## 8. Подготовка к Google Play

- Подпись: Play App Signing, upload key хранится вне репозитория (`*.keystore` в .gitignore), в CI — через секреты.
- Target API 36, 64-bit, поддержка 16 KB page size (собирать на актуальном патче Unity 6 LTS).
- Data safety форма: офлайн-игра без аккаунта → «данные не собираются» (если ads/аналитика добавлены в форке — обновить).
- Возрастной рейтинг (IARC): бильярд без ставок — «Everyone»/3+. Важно: никаких механик с деньгами «на ставку», иначе попадаем в категорию симуляции азартных игр.
- Политика конфиденциальности (страница на GitHub Pages).
- Тестирование: internal → closed testing (для новых личных аккаунтов разработчика Play требует закрытый тест с группой тестировщиков перед продакшеном) → production.
- Pre-launch report Play Console + Android Vitals: ANR < 0.47%, crash < 1.09%.

## 10. Риски

| Риск | Митигирование |
|---|---|
| «Ощущение» физики не нравится игрокам | всё в `PhysicsConfig`; плейтесты с реальными игроками с этапа 1 |
| Рассинхрон float между устройствами (онлайн) | double + фиксированный шаг + никаких `Math.FMA`/SIMD в ядре; хэш состояния после удара |
| Лузы «съедают»/«выплёвывают» неестественно | капсульные губки уже есть; при необходимости 3D-модель лузы (дно, задняя стенка) в той же модели импульсов |
| ИИ тормозит на слабых телефонах | грубый шаг для отбора, бюджет симуляций в `AiProfile`, ограничение времени раздумья |
| Права на ассеты в open-source | только свои/CC0; список источников в `docs/CREDITS.md` |
